1 Scope Overview

This plan covers all development work required to deliver Phase 1 of the ElitePetz improvement roadmap. It is broken into six groups: foundational bug fixes, the manual onboarding lifecycle and admin dashboard, the claim and notification system, public-facing certification visibility, the email handling and audit trail system, and the Founding Breeders positioning layer. All work runs on the existing Wix Studio + Velo platform — no infrastructure changes. Updated May 8, 2026 to reflect the full scope of blueprint v2.6.

What this plan delivers A stable ID generation system with no race conditions or deletion risk; the complete manual onboarding lifecycle (Approved → Invited → Active → Suspended / Revoked / Expired / Renewed); a full admin dashboard with state-sensitive actions, data validation checkpoint, duplicate prevention, record origin tracking, admin ownership, contact attempt logging, reason enforcement, internal notes, and a dedicated Needs Attention tab; a configurable claim link system with backend state guard; updated public certification visibility for all states including post-active; the Verify page trust explanation section (content supplied by Pavel); a robust email failure and retry system with confirmed asset inclusion on renewal; a complete StatusHistory audit trail for the manual path; and Founding Breeders positioning fields including the foundingBadgeVariant slot.
Estimates All hour ranges reflect development and integration testing time on the Wix + Velo platform. The standard application path and all existing payment, email, and media functionality are not touched.

2 Group A — Foundation Fixes

Current production bugs identified in the codebase audit. These must be resolved first — they underpin the reliability of everything built on top.

Bug Fixes & Infrastructure
Resolving production-breaking issues in the existing system
6–9 hours
F-01 IDRegistry — Race Condition & Deletion Fix
High Complexity 5–7 hrs

The current ID generation reads a record count, computes the next ID, then writes — three separate operations with no lock. Two concurrent requests can read the same count and generate the same ID; Wix CMS accepts both inserts silently. Separately, deleting records rewinds the counter, causing previously issued IDs to be reassigned. Both are production-breaking for a platform whose core promise is a permanent, non-reusable certification identity.

What will be built
  • IDRegistry CMS collection — dedicated counter with lock fields (lockedBy, lockedAt, status)
  • IDLog CMS collection — permanent record of every issued ID
  • Rewritten generateCertificationId() using IDRegistry — never counts live records
  • Rewritten generateReferenceId() for Application IDs — same pattern
  • Stale lock detection — locks older than 15 seconds auto-release on next request
  • Retry logic — up to 3 retries at 300ms intervals
F-02 Query Limit Fix — 50-Record Truncation
Low Complexity 1–2 hrs

Wix CMS queries default to 50 records. Every query in the backend that does not explicitly set a limit silently truncates results — making the 51st application, certification, or complaint invisible to admin. This gets worse as the registry grows.

What will be built
  • Audit of all wixData.query() calls across all backend modules
  • Explicit .limit(1000) added to all admin-facing queries
  • Pagination handling added to any query that could realistically exceed 1000 records in future
F-03 Scheduled Job — Certification Expiry
Already Fixed 0 hrs

The expiry job in jobs.config was not running due to a configuration error — certifications were never being automatically expired. This has been resolved. No further work required.

3 Group B — Manual Onboarding Lifecycle

The core new feature: the Approved → Invited → Active lifecycle for admin-created certifications, including the admin dashboard to create and manage them, with full admin override at every stage.

Manual Onboarding Lifecycle
Backend state machine, admin dashboard, and visibility controls
16–26 hours
F-04 Lifecycle State Machine — Full Manual Path
High Complexity 5–8 hrs

The backend foundation for the manual onboarding path. Enforces the complete state machine — all creation, promotion, and terminal transitions — with explicit guards at every step. Revoked is a hard lock: no transitions, no emails, and the cron job explicitly skips it. ClaimActivated is restricted to Approved and Invited states at the backend level.

What will be built
  • New onboardingType field: "standard" or "manual" — cross-path guard on every function
  • New manualOnboarding.web.js backend module — all manual path logic isolated here
  • Permanent Certification ID assigned at creation via IDRegistry (F-01)
  • All forward transitions: Create→Approved, Approved→Invited, Approved→Active (direct), Invited→Active, Invited→Approved (unpublish)
  • Post-active transitions: Active→Suspended, Suspended→Active (Reinstate), Active/Suspended→Revoked, Active→Expired (cron)
  • Renewal transition: Expired→Active (Renewed) — same Cert ID, new dates, renewal email fires
  • Revoked hard lock — backend explicitly blocks all transitions and all emails from Revoked state
  • Cron job updated to skip Revoked records when running the expiry check
  • ClaimActivated backend guard: validates cert is Approved or Invited before processing; rejects all other states with appropriate message
  • Reason field required at backend level for Suspend, Revoke, and Direct Activation — function rejects calls without it
  • invitedAt timestamp set on Approved→Invited transition

F-05 Admin Certifications Management Dashboard
High Complexity 6–9 hrs

The admin-facing page where all manual certifications are created and managed. Covers the full lifecycle — from creation through to post-active states — with context-sensitive actions, reason enforcement dialogs, internal notes, a dedicated Needs Attention tab, data validation before activation, and duplicate prevention at creation.

What will be built
  • Create Certification form — breeder name, breed, location, email; isFounding checkbox; foundingSequenceNumber input; foundingBadgeVariant text field; sourceType dropdown (manual_outreach / application / imported / referral); sourceNote text field; assignedAdminId selector; system assigns Cert ID on submission
  • Duplicate prevention check — on form submission, checks existing records for matching breeder name or email; displays warning banner if match found (not a hard block); logs DuplicateWarningAcknowledged to StatusHistory if admin proceeds
  • Certifications table — Breeder Name, Cert ID, Status pill, Last Updated, Actions
  • Status filter tabs — All / Approved / Invited / Active / Suspended / Revoked / Expired + ⚠ Needs Attention (count badge)
  • Full action set per state:
    • Approved: Publish as Invited, Activate Directly, Send Claim Email, Edit
    • Invited: Activate, Resend Claim Email, Edit, Unpublish
    • Active: View Verification, Resend Assets Email, Edit, Suspend, Revoke
    • Suspended: Reinstate, Revoke, Edit, View Verification
    • Expired: Renew, View Verification
    • Revoked: View Verification, Add Internal Note (read-only otherwise)
  • Data validation checkpoint — Activate button visually disabled until breeder name, location, and breed are all confirmed present; UI-level gate only (not backend enforced)
  • Reason enforcement dialog — modal that requires reason text before confirming Suspend, Revoke, or Direct Activation; calls backend with reason parameter
  • Internal notes UI — text input on record detail view; each note appended to StatusHistory as InternalNote; shown in chronological order, admin-only
  • Contact tracking fields on record detail view — admin can log lastContactAttemptAt (date picker) and contactMethod (email / instagram / facebook / phone) for each outreach attempt; never shown publicly
  • Each button calls corresponding backend function; table refreshes on state change

F-06 Admin Lifecycle Control Functions
Medium Complexity 2–4 hrs

Backend functions for all admin-triggered lifecycle transitions beyond the core Approved→Active flow. Covers the full post-active lifecycle: suspend, reinstate, revoke, and renewal. Each function validates the current state, enforces reason requirements, and logs to StatusHistory.

What will be built
  • adminActivateCertification(certId, reason) — Approved/Invited → Active; invalidates open claim token; reason required
  • suspendCertification(certId, reason) — Active → Suspended; reason required; cert remains publicly visible with Suspended label
  • reinstateCertification(certId, reason) — Suspended → Active; re-activates publicly
  • revokeCertification(certId, reason) — Active/Suspended → Revoked; hard lock applied; reason stored permanently in StatusHistory; reason required
  • renewCertification(certId) — Expired → Active (Renewed); same Cert ID; new activationDate and expirationDate; triggers renewal email (separate template)
  • All functions reject calls on Revoked records — hard lock enforced at function level

4 Group C — Claim & Notification System

The optional path that allows breeders to take ownership of and activate their own profiles. None of this blocks admin control — it runs in parallel to the admin workflow.

Claim & Notification
Token-based breeder activation and email system
6–10 hours
F-09 Claim Token System
Medium Complexity 3–5 hrs

When admin sends a claim email, the system generates a secure one-time token attached to the certification record. When the breeder clicks the link, the token is validated and the certification activates immediately. The token cannot be reused, replayed, or used after expiry.

What will be built
  • Token generation: UUID v4 stored as claimToken on the Certifications record
  • Token fields: claimToken, claimTokenExpiry, tokenUsed
  • Claim validation endpoint: checks token exists, not expired, not already used
  • State guard (backend enforced): rejects activation if cert is not Approved or Invited — Suspended, Revoked, Expired, and Active are all hard-blocked with appropriate response message
  • On valid claim: marks token as used and transitions record to Active atomically
  • On admin activation: any outstanding token for the record is invalidated
  • Configurable expiry: reads from admin settings (default 30 days, disableable)
Depends on

F-10 Claim Email — Send & Resend
Low Complexity 1–2 hrs

Admin can send a claim email from either Approved or Invited state. The email contains the breeder's certification details and their unique claim link. Resending invalidates the old token and generates a fresh one.

What will be built
  • sendClaimEmail(certificationId) backend function — generates token and sends email via Wix CRM Triggered Emails
  • Email template: includes breeder name, Certification ID, and unique claim link
  • Resend logic — old token invalidated, new token generated, email re-sent
  • Connected to "Send Claim Email" (Approved) and "Resend Claim Email" (Invited) buttons in admin dashboard
Depends on
F-09 Claim Token
F-11 Admin Configuration Settings
Low Complexity 2–3 hrs

Four settings that control Phase 1 behaviour, all adjustable by admin without a code change. Stored in a dedicated AdminConfig CMS collection and read dynamically by backend functions at runtime.

What will be built
  • Claim Token Expiry — toggle on/off with configurable duration (default: 30 days). When off, tokens never expire until used or invalidated.
  • Auto-Send Claim Email on Publish — toggle on/off (default: off). When on, claim email fires automatically on Approved→Invited transition.
  • Invite No-Response Alert Threshold — number of days after publishing as Invited before the record surfaces in the Needs Attention tab (default: 7 days). Can be disabled.
  • Email Max Retry Attempts — how many automatic retries before emailUnreachable is set (default: 3). Set to 1 to disable retries.
  • Settings stored in AdminConfig CMS collection; settings UI in admin panel Settings tab

F-15 Email Failure Handling & Needs Attention Tab
High Complexity 4–6 hrs

Wraps all email send calls in try/catch, logs failures, retries automatically up to the configured limit, and flags unreachable records. Surfaces all issues in a dedicated Needs Attention tab in the admin dashboard — email failures, stale invitations, and expired claim tokens in one unified queue.

What will be built
  • New fields on Certifications: emailFailedFlag (Boolean), emailFailedType (Text), emailUnreachable (Boolean)
  • Try/catch wrapper on all email send calls — on failure: set flag, log ActivationEmailFailed / ClaimEmailFailed / AssetsEmailFailed to StatusHistory
  • Auto-retry logic: retries up to configured max attempts (F-11), then sets emailUnreachable = true and logs EmailUnreachable
  • Needs Attention tab query combining: emailFailedFlag = true OR emailUnreachable = true OR (status = Invited AND invitedAt older than threshold) OR (claim token expired AND status in Approved/Invited)
  • Needs Attention tab UI: rows with issue-type badges (Email Failed / No Response / Token Expired / Email Unreachable), context-sensitive action buttons per issue
  • Three emailUnreachable resolution actions:
    • Mark as Delivered Manually — clears flag, logs MarkedDeliveredManually
    • Update Email + Retry — corrects address, triggers fresh send, resets retry counter
    • Proceed Without Email (Silent) — closes issue, logs EmailSkipped

F-16 StatusHistory Audit Log — Manual Path Extension
Medium Complexity 2–4 hrs

Extends the existing StatusHistory collection to cover the full manual onboarding path. Every state transition, email event, admin action, and internal note is recorded as an append-only log entry. The actorType field is added to enable filtering by actor category. A shared helper keeps logging consistent across all features.

What will be built
  • New actorType field on StatusHistory: "admin" / "breeder" / "system"
  • Shared addStatusHistory(certId, action, actorId, actorType, reason) helper in utilts.web.js — used by every feature to ensure consistent logging
  • All new action values wired: ManualCreated, PublishedAsInvited, Unpublished, ActivatedDirect, ActivatedFromInvited, ClaimEmailSent, ClaimEmailResent, ClaimActivated, ActivationEmailSent, AssetsEmailResent, Suspended, Reinstated, Revoked, Expired, Renewed, ActivationEmailFailed, ClaimEmailFailed, AssetsEmailFailed, EmailUnreachable, MarkedDeliveredManually, EmailUpdatedAndRetried, EmailSkipped, InternalNote
  • Internal notes stored as StatusHistory entries with action: "InternalNote", note text in reason field — append-only, admin-only, never publicly exposed
  • Admin dashboard record detail view shows full StatusHistory for each certification, filtered to exclude InternalNotes from any public-facing query
Depends on
