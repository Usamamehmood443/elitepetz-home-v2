01 System Architecture Summary

ElitePetz is a pet breeder certification platform built on Wix Studio + Velo. It manages the full lifecycle of breeder certifications — from public application submission through admin review, payment, badge generation, activation, auto-expiry, suspension, revocation, and reinstatement. A public-facing registry allows anyone to verify a certification by its unique ID.

04 Current Certification Workflow

The complete end-to-end flow as it exists in code today:

1
Applicant Submits Application

Page: Certification Application. User fills form (name, email, country, breed, description, declaration checkbox, captcha). Code calls wixData.insert("Applications", {...}) with status: "Submitted" and paymentStatus: "Pending". Reference ID generated as EP-YEAR-NNNN. Email VDU6G9m (confirmation) sent to applicant.

2
Admin Reviews in Admin Portal

Admin Portal → Applications tab → clicks View → ApplicationsDetails state shows all application fields + status history.

3a
Admin Approves Application

Lightbox: Approve Application. Calls approvedApplication(id, memberId, reason). Application status → Approved. StatusHistory record: action "Approved". Email VDUHs9m sent with payment link: https://www.elitepetz.com/payments?id={referenceId}.

3b
Admin Rejects Application

Lightbox: Reject Application. Calls rejectApplication(). Application status → Rejected. StatusHistory: "Rejected". Email VDUMSa5. Terminal state.

4
Applicant Pays Online

Page: Payments (/payments?id={referenceId}). Reads payment amount from Wix Secrets. Validates application is Approved and not yet Paid. Calls createPayment() → wixPayFrontend.startPayment(). On success, updates paymentResponse field on Application. Note: Does NOT auto-set paymentStatus = "Paid" — admin must still manually confirm.

5
Admin Confirms Payment → Certification Record Created

Lightbox: ConfirmPayments. Calls confrimPayments(applicationId, memberId, reason). Sets Application paymentStatus = "Paid". Creates a new Certifications record with status "Approved", paymentStatus "Paid", certificationId generated as EP-CERT-YEAR-NNNN-XXX. StatusHistory: "Paid". Email VDaC8OZ.

6
Admin Activates Certification + Badge Generation

Lightbox: Activate Certification. Renders 6 badge PNGs using canvas Web Components (3 sizes × dark/light: 300×100, 600×200, 1080×1080). Uploads each PNG to Wix Media Manager. Calls activationCertification(certId, memberId, reason): sets certificationStatus = "Active", activationDate = now, expirationDate = +12 months. StatusHistory: "Activated". Email VE3TXBV sent with 6 badge download links + verification link.

7
System Auto-Expires (Daily Cron)

Scheduled at 20:00 UTC. expiredCertification() paginated query finds all non-Expired certifications where expirationDate ≤ today. Sets certificationStatus = "Expired". Bulk inserts StatusHistory records (actorId: "system"). No email sent.

8
Admin Suspends (from Active)

Lightbox: Suspend Certification. suspendCertification(). Status → Suspended. History + email VEFanj2.

9
Admin Reinstates (from Suspended)

Lightbox: Reinstate Certification. reinstatedCertification(). Status → Active (dates not reset). History + email VEFL8LR with verification link.

10
Admin Revokes (from Active or Suspended)

Lightbox: Revoke Certification. revokeCertification(). Status → Revoked. History + email VEFVrBN (includes previous status + reason). Terminal state in UI.

Status State Machine

Applications:
  Submitted ──► Approved ──► (paymentStatus: Pending ──► Paid)
  Submitted ──► Rejected  [terminal]

Certifications:
  Approved ──► Active ──► Suspended ──► Active  (reinstated)
               Active ──► Revoked              [terminal]
               Suspended ──► Revoked           [terminal]
               Active ──► Expired              [auto, terminal]

07 What is Implemented vs. Missing

Fully Implemented

  • Public application submission form (validation, CAPTCHA, reference ID generation, email confirmation)
  • Admin Portal with all lifecycle actions accessible via lightboxes (approve, reject, confirm payment, activate, suspend, revoke, reinstate)
  • Full email notification system across all state transitions (8 active email templates)
  • Badge generation pipeline: canvas Web Components render 6 badge variants (3 sizes × dark/light), upload to Media Manager, deliver download links via email
  • Daily auto-expiry cron job with batch pagination for scale
  • StatusHistory audit trail written at every state transition
  • Public certification verification page via URL slug
  • Admin review tables for complaints and inquiry forms with evidence file download
  • Payment page with Wix Pay integration and fee read from Secrets

Partially Implemented / Stubbed

  • Payment auto-confirmation: Wix payment fires but does not auto-set paymentStatus = "Paid" — admin must manually confirm via ConfirmPayments lightbox
  • Activation email in backend: Commented out in activationCertification() — email only fires via the lightbox UI path
  • HTTP badge endpoint (get_badge600): Implemented with Jimp but unclear if it is used in production; runs parallel to the canvas badge system
  • SPI automation providers: All 4 registered but have empty invoke() stubs
  • Administrative inquiry email: Function exists but is commented out
  • getCertificateDownloadLinks: Implemented in mediaUtilts.web.js but unclear where it is called from

Not Implemented / Missing

  • No Wix lifecycle event handlers (events.js is empty)
  • No expiry notification email to the breeder when their cert expires
  • No reinstate path from Revoked status in the Admin Portal UI (backend supports it, UI does not surface it)
  • No renewal flow after expiry

08 Risks, Gaps & Issues

Critical Security Risk

🔴 No authorization on admin web methods permissions.json grants anonymous users the right to invoke ALL web methods including approvedApplication, rejectApplication, suspendCertification, revokeCertification, etc. Any unauthenticated external caller can manipulate certification status. There are no auth checks inside the methods themselves. This must be addressed before public launch.

Functional Gaps

⚠ Payment flow disconnect The Payments page stores paymentResponse on success but does NOT update paymentStatus = "Paid". A Wix payment can succeed online and the applicant receives no automated next step. Admin must manually notice and confirm via the ConfirmPayments lightbox before a Certifications record is created.
⚠ jobs.config filename typo The scheduled cron references /utils.web.js but the actual file is utilts.web.js. The daily auto-expiry job likely never runs, meaning certifications never expire automatically.
ℹ No expiry email to breeders When a certification expires (auto or manual), no email is sent. Breeders would only discover expiry by checking the public directory or being told.

Bugs

⚠ applicationsTable.js — filter logic bug In applyFilter(), when both the status filter AND payment filter are set to non-"all", the code uses OR logic (statusMatch || paymentMatch) instead of AND. This returns all Approved applications OR all Pending-payment applications, rather than the intersection.
⚠ getApplications() and getCertification() — missing .limit() Neither query sets a .limit() value. Wix CMS defaults to 50 items per query. Once there are more than 50 applications or certifications, these queries will silently truncate data. The expiredCertification() cron correctly uses paginated batches of 1000 — the same pattern needs to be applied to the admin queries.
ℹ getImageByname() ignores the name parameter The function calls files.searchFiles() without passing the searchOptions variable, always returning all files instead of filtering by name.

Architecture / Design Issues

ℹ Certification is created at payment confirmation, not at approval There is a commented-out block in approvedApplication() that would have created the Certifications record at the approval step. Current design creates it only when payment is confirmed. This is likely intentional but means no Certifications record exists in the gap between approval and payment confirmation.
ℹ Badge generation is tightly coupled to the UI The 6 badge PNGs are generated in the browser (canvas) inside the Activate Certification lightbox. If the lightbox errors mid-way, some badges may upload while others do not, and the email may send with broken download links. There is no retry mechanism or atomic guarantee.
ℹ badge1080.js uses window.parent.postMessage instead of CustomEvent The 1080×1080 badge component sends results via window.parent.postMessage() while the other two badge components dispatch rendered CustomEvents. The lightbox handles this correctly today using element.onMessage(), but the inconsistency makes the components harder to understand and maintain.
ℹ Two parallel badge generation approaches The get_badge600 HTTP endpoint (using Jimp on the server) and the canvas-based lightbox badge generation are two separate implementations for the same purpose. It is unclear which one is the production path or if both are used in different contexts.
